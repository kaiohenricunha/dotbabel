# §4 — Data Flow / Components

> Current state analysis + target architecture.

## Current State

[current-state/analysis.md](../current-state/analysis.md) holds the grounded audit (DOC-2). In short: specs carry commands but no criteria, and the pull request stage runs tests but checks only the test plan that the author wrote. The quality layer cannot trigger a tool by path, and `critical_paths` is parsed but unused. Nothing checks the deployed system beyond commit SHAs and the npm registry.

## Shared State

- **Evidence comments** are the only state shared between verification and the merge gate. Each full run posts a new comment and minimizes the tool's older evidence comments as outdated. No evidence comment is ever edited, and the gate ignores any comment that was (KD-2, SEC-3). The marker names the head SHA, so a new push makes old evidence stale without a clean-up step (REL-2).
- **`spec.json`** is shared by authoring, validation, verification, and the gate. The gate reads it at the pull request head, to see the specs that the pull request adds, and at the base ref, to detect a weakened criterion (REL-15).
- **`.dotbabel.json`** is shared by quality runs, the criteria command, and the gate. The gate reads its `criteria` key at the base ref, so a pull request cannot relax its own gate (REL-16).
- **The trust allowlist** is user scope. Every component reads it, and none writes it.
- **Synchronization** needs nothing beyond Git and GitHub, because every run reads fresh state. When two verification runs happen on one head, both comments are valid, and the gate accepts any trusted, unedited comment for that head.

## Target Architecture

### Flow 1 — Criteria-first authoring

1. The `spec` skill writes `acceptance_criteria` for each work unit into `spec.json` with status `planned`, and each §6.3 prompt lists the same test names (KD-1, KD-15).
2. The unit that adds a criterion's tests sets that criterion to `active` in the same pull request.
3. `dotbabel-validate-specs` checks only the shape (Q-5).
4. The `validate-spec` audit reports a spec with no criteria as an INFO finding, and its Phase 4 runs `dotbabel criteria verify --spec <id>`.

### Flow 2 — Verification inside `review-pr`

1. At step 11 (`skills/review-pr/SKILL.md:210`), `review-pr` reads each named test of the active criteria and opens a review thread for any test that asserts nothing or mirrors the implementation (KD-4).
2. `review-pr` pushes the fixes for those threads with its other review fixes, then resolves the threads at step 12.
3. Step 13 may rebase and push (`skills/review-pr/SKILL.md:297`). After step 13, as its last action, `review-pr` runs `dotbabel criteria verify --pr <N> --post` (REL-18).
4. The command checks its preconditions: local `HEAD` equals the pull request head, the worktree is clean except for `.dotbabel/`, the pull request is not a fork, and no untrusted author changed an active criterion's `argv` (SEC-1).
5. The command parses `## Spec ID` with the shared parser (ARCH-6) and loads each listed spec. It exits 0 with a notice when no listed spec declares an active criterion.
6. For each active criterion, the command checks that every named test file exists and contains the test name, deletes the report path, runs `argv` through the quality runner, and confirms each test (KD-3). A planned criterion is recorded as `pending` and does not run (KD-15).
7. The command redacts and truncates the output, builds the payload, posts a new evidence comment pinned to the head SHA, and minimizes its older evidence comments (KD-2).
8. If any active criterion is not `pass`, `review-pr` reports `BLOCKED`, and the conductor stops before `local-attest` (REL-10).
9. If the head moves later, `/merge-pr` finds `CRITERIA_EVIDENCE_STALE`, runs the command again, and checks the gate again before it merges (REL-18).

### Flow 3 — Merge gate

1. `dotbabel pr-stack gate --gate merge` fetches the body, files, mergeability, head and base SHAs, comments with edit metadata, and check runs.
2. It parses the Spec IDs with the shared parser, reads each spec at the head SHA, and reads the same specs and the `criteria` configuration at the base SHA (REL-16).
3. It sets the required criteria to the active criteria of the linked specs at the head.
4. `checkMergeGate` evaluates the existing reasons, `CRITERIA_SPEC_UNKNOWN`, `CRITERIA_WEAKENED`, the evidence reasons in §5, and the CI check when `require_ci_check` is true (KD-16).
5. When `criteria.enforcement` at the base is `warn`, criteria reasons appear under `warnings`, and `ok` ignores them (KD-14).

### Flow 4 — Quality diff run

1. The scope step resolves the changed files.
2. The planner drops a tool whose `paths` match no changed file, unless `--all` is set, and records `not_triggered` (KD-5).
3. When a changed file matches `critical_paths`, the planner adds the test plan of every component in every profile and ignores `--path` narrowing for those plans. The evaluator selects `correctness.tests` for that run, so a failing escalated test fails the run (KD-6).
4. The `deep` profile adds detected mutation tools, and the parsers score only mutants on changed lines (KD-7).

### Flow 5 — Post-deploy

1. `release-conductor verify` runs its three registry checks (`skills/release-conductor/SKILL.md:225-249`).
2. When a deploy target exists, it runs `deploy-ops.mjs status` and then `deploy-ops.mjs smoke`. Otherwise it reports both as `SKIPPED`.
3. Any drift or failed smoke check makes the verdict FAIL. The skill then recommends `/rollback-prod` and stops (KD-13).

### Flow 6 — Local hooks

1. The pre-push hook runs `dotbabel quality check --profile fast` against the merge base with the upstream branch (KD-11). A critical-path change adds tests to that run, and a failing test blocks the push (KD-6).
2. With `CHECK_ON_STOP_TESTS=1` in a trusted repository, `check-on-stop.sh` runs the related tests for files changed in the turn (KD-12).
3. In an agent session that registers it, the evidence guard hook checks every shell command before it runs (KD-16).

### Key Decisions

<!-- Tag each as KD-N for cross-referencing -->

- **KD-1 — Acceptance criterion shape. Decided 2026-09-11.** A criterion has an id, separate `given`, `when`, and `then` statements, the tests that prove it as a file path plus a test name, and one `argv` command that runs those tests. Two existing conventions set this shape. Specs already list TDD tests as a file followed by test names (`docs/specs/cli-bootstrap-command/spec/6-implementation-plan.md:51-57`), and quality tools already declare commands as `argv` arrays with no shell strings (`docs/quality.md:175`). The repository owns the command, so dotbabel never guesses how a test runner filters tests. The validator checks only the shape, because a spec exists before its tests do. At verification time, dotbabel checks that each named test appears in its file, runs the command, and records the exit code and the output tail. §5 holds the schema.
- **KD-2 — One trusted, append-only evidence comment for each run. Decided 2026-09-11, hardened after review.** The owner delegated this choice, and the recommended option was adopted, then hardened by the pull request review. Each full run posts a new comment. Its first line is exactly `<!-- dotbabel-criteria verified-sha=<head SHA> -->`, its second line carries the payload, and a readable table with redacted output tails follows. The payload holds no output text, only a SHA-256 hash of each tail, so no output hides from GitHub secret scanning inside base64. The command minimizes its own older evidence comments with the GraphQL `minimizeComment` mutation and the `OUTDATED` classifier. It never edits a comment, because a user with write access can edit anyone's comment (DOC-22). The gate reads comments through GraphQL with `authorAssociation` and `lastEditedAt`. It accepts any comment whose author association is in `criteria.trusted_associations`, whose `lastEditedAt` is null, and whose marker names the head SHA, the same match rule as `isAttested` (`plugins/dotbabel/src/local-attest-lib.mjs:70-87`). The marker helpers in `plugins/dotbabel/src/local-attest-lib.mjs:47-110` move into a shared module, and the local-attest marker text stays unchanged. The pull request body was rejected because anyone who can edit it can forge the evidence (A-6). Commit statuses and check runs as the evidence store were rejected in A-7, and comments edited in place in A-14.
- **KD-3 — A pass needs confirmed tests, not only exit code 0. Decided 2026-09-11.** A criterion may declare an optional `report` with format `junit-xml` and a repository-relative path. A criterion passes only when its command exits 0 and each named test is confirmed. With a report, a testcase confirms a test when its name equals the test name, or ends with it after `>`, `::`, `.`, or `/`, and when it has no `failure`, `error`, or `skipped` child. Without a report, the test name must appear in the command output. Exit code 0 with a missing name makes the criterion `unconfirmed`. The command deletes `report.path` before the run, and a report that is missing after the run makes the criterion `error`, so a report from an earlier run can never confirm a test. This closes the zero-test false pass, where a filter that matches nothing still exits 0, as `go test -run` does. JUnit XML is the de facto format for per-test results (DOC-15).
- **KD-4 — Deterministic gates, advisory AI judgment. Decided 2026-09-11.** Merge-gate verdicts come only from evidence that commands produce and from deterministic quality metrics. The review agent's test-quality judgment opens review threads, which `review-pr` must fix or answer before it resolves them. The agent never writes a criterion status. When the repository configures a mutation tool, the mutation score is the deterministic backstop. Model output varies between runs and can be steered by instructions hidden in the content it reads (DOC-17), so it informs a gate and never decides one.
- **KD-5 — Path-triggered tools and the `regression` capability. Decided 2026-09-11.** Any configured quality tool may declare `paths`, an array of repository-relative globs. With `paths`, the planner keeps the tool only when a changed file matches, or when `--all` is set. Otherwise the result state is `not_triggered` with verdict `info`. A new `regression` capability runs in `pr` and `deep` and feeds a new hard rule, `correctness.regression`. Like `correctness.tests`, the rule accepts no exception and no baseline. This replaces `regression_paths` (Q-2): the repository owns the check, and dotbabel decides when it runs and records its verdict.
- **KD-6 — `critical_paths` requires the full suite. Decided 2026-09-11, corrected after review.** When a changed file matches `critical_paths` (`plugins/dotbabel/src/quality/config.mjs:15`, `:90`, `:191`), the planner adds the test plan of every component in every profile, `fast` included. It also ignores `--path` narrowing for those plans, and the envelope lists the matched files in `critical_matches`. Without a `--path` filter, the `pr` and `deep` profiles already run whole-component test commands (`plugins/dotbabel/src/quality/discovery.mjs:112-116`), so the escalation matters where the scope is narrow: the `fast` profile in the pre-push hook, and `--path` runs. The evaluator must also count the escalated result. Today `evaluateQuality` skips an execution whose rule does not list the current profile (`plugins/dotbabel/src/quality/evaluate.mjs:22`), and `correctness.tests` lists only `pr` and `deep` (`plugins/dotbabel/src/quality/policy.mjs:32`). When `critical_matches` is not empty, rule selection adds `correctness.tests` to the current profile, and each adapter's profile filter lets the `test` capability through. The rule-floor line at `CLAUDE.md:50` changes to name `critical_paths`.
- **KD-7 — Detect configured mutation tools and score changed lines. Decided 2026-09-11.** Adapters detect a mutation tool only from repository configuration: a Stryker configuration file for JavaScript and TypeScript, mutmut configuration in `pyproject.toml` or `setup.cfg` for Python, and a Gremlins configuration file for Go. P-C4 confirms each file name against the tool's documentation. The plans run only in `deep`. Parsers read per-mutant results and compute the score as detected ÷ valid × 100 for mutants that start on a changed line (DOC-16). Detected means killed or timed out, and valid means detected, survived, or with no coverage. With no mutant on a changed line, the rule reports `not_applicable`. The current `stryker-json` parser reads only a top-level score (`plugins/dotbabel/src/quality/reports.mjs:114-117`), so P-C4 replaces it and checks the result against a real captured report.
- **KD-8 — Built-in Python and Node plans for declared tools. Decided 2026-09-11.** For Python, plan `pytest` when the component declares pytest configuration: `[tool.pytest.ini_options]` in `pyproject.toml`, a `pytest.ini` file, `[pytest]` in `tox.ini`, `[tool:pytest]` in `setup.cfg`, or a root `conftest.py`. Run it under `uv run` or `poetry run` when the matching lockfile exists (`docs/quality.md:101`). Plan coverage as `pytest --cov --cov-report=json:<path>`, parsed as `coveragepy-json`, only when `pytest-cov` is a declared dependency. For Node, when no coverage script exists, plan `vitest run --coverage` with the JSON reporter when a Vitest coverage provider is a declared dev dependency. Plan `jest --coverage` with the JSON reporter when Jest is declared. Both reports parse as `istanbul-json`. A repository script or Make target keeps priority (`plugins/dotbabel/src/quality/adapters/node-tools.mjs:36-45`).
- **KD-9 — Remove `regression_paths` and `verification_commands`. Decided 2026-09-10.** Delete both keys from `docs/repo-facts.json:38`, `plugins/dotbabel/templates/docs/repo-facts.json:16-17`, and `examples/minimal-consumer/docs/repo-facts.json:16`. Rewrite `CLAUDE.md:50` and regenerate the host instruction files. Replace step 5 of `commands/merge-pr.md:59-67`, its template copy, and `.github/prompts/merge-pr.prompt.md` with the quality verdict. `dotbabel doctor` warns when a repository still gives either key a value, and it names the replacements (OPS-6).
- **KD-10 — Consumer CI templates verify but never post evidence. Decided 2026-09-11, corrected after review.** `test.yml` runs on `pull_request`. A classify job honors a trusted local-attest marker for the head SHA and fails closed, as this repository's `.github/workflows/test.yml` does. When the job finds no marker, a verify job runs `dotbabel quality check --profile pr`. A separate job named `dotbabel criteria` runs `dotbabel criteria verify --pr <N>` when a linked spec declares an active criterion. That job checks out `github.event.pull_request.head.sha` instead of the default merge commit, so the command's head check passes, and it authenticates `gh` with `github.token`. The local-attest skip never skips the `dotbabel criteria` job. Both jobs upload their JSON reports. `quality.yml` runs the `deep` profile weekly and on manual dispatch, following `.github/workflows/quality.yml`. CI never posts the evidence comment. Its bot identity is not a trusted association by default, and a second writer would race the local run. The CI check is the independent re-run that KD-16 level 2 can require. Both templates meet SEC-7 and SEC-13, and they mark their language setup steps for consumers to edit.
- **KD-11 — An opt-in pre-push hook that never traps a push. Decided 2026-09-11.** `githooks/pre-push` runs `dotbabel quality check --profile fast` against the merge base with the upstream branch. Quality exit 1 blocks the push. Exit 2, a timeout, or a missing `dotbabel` prints a notice and allows the push. `BYPASS_PRE_PUSH=1` and `git push --no-verify` skip the hook. Activation stays manual with `git config core.hooksPath githooks`, because the hook runs repository code, and the docs say so next to that command.
- **KD-12 — Related tests at turn end, opt-in and trusted only. Decided 2026-09-11.** `check-on-stop.sh` gains a tests stage that runs only with `CHECK_ON_STOP_TESTS=1` in a trusted repository. It uses each runner's own scoping, as `review-pr` already does (`skills/review-pr/SKILL.md:132`): `vitest related --run`, `jest --findRelatedTests`, `go test` on touched packages, and `pytest` on touched test files. `CHECK_ON_STOP_TIMEOUT` bounds the stage (`plugins/dotbabel/hooks/check-on-stop.sh:78`), and the give-up counter still stops after two blocks (`:80`).
- **KD-13 — Smoke checks live with the deploy targets. Decided 2026-09-11.** Each target in `.claude/deploy-targets.json` (`skills/deploy-status/scripts/deploy-ops.mjs:143-155`) may declare a `smoke` array. `deploy-ops.mjs smoke` runs `http` checks, which use GET only, and `command` checks, which use `argv`. The helper stays self-contained, because scaffolded copies cannot import package source, so it carries its own guards for URLs, redirects, the environment, redaction, and time. The `smoke-test` skill wraps the command. `release-conductor verify` adds deploy status and smoke results when a target exists. On a failure, it recommends `/rollback-prod` and stops, because the rule floor forbids production changes without explicit instruction.
- **KD-14 — Enforcement, trust, pass-through, and timeout settings. Decided 2026-09-11, extended after review.** `.dotbabel.json` gains a `criteria` object with five keys. `enforcement` is `block` by default, or `warn`. `trusted_associations` defaults to `["OWNER"]`. `timeout_seconds` defaults to 600 and accepts 1 through 3600, the quality tool bounds in `plugins/dotbabel/src/quality/config.mjs:67-68`. `pass_env` lists the environment variable names that criterion commands receive, the same mechanism as `dotbabel quality --pass-env` (`plugins/dotbabel/bin/dotbabel-quality.mjs:24`, `:52`). `require_ci_check` turns on KD-16 level 2. The project config loader (`plugins/dotbabel/src/project-sync.mjs:104`) and `schemas/dotbabel.config.schema.json` validate the object. The merge gate reads it at the base ref, so a pull request cannot relax its own gate. `warn` is the documented rollback switch in §6.6.
- **KD-15 — Planned and active criteria. Decided 2026-09-11 after review.** Each criterion has an optional `status`, `planned` or `active`, and an absent status means `active`. A planned criterion is shape-checked and listed, and the evidence records it as `pending` without running it. The unit that adds a criterion's tests sets it to `active` in the same pull request. A spec can therefore state all of its criteria before any code exists, while each unit's pull request is gated only on the criteria it delivers. A criterion that is active at the base ref and planned or missing at the head fails the gate with `CRITERIA_WEAKENED`. A `## Criteria change rationale` section in the pull request body turns that reason into a warning, following the existing `## No-spec rationale` pattern.
- **KD-16 — Two assurance levels for evidence. Decided 2026-09-11 after review.** At level 1, the default, the gate trusts the evidence comment (KD-2), and a PreToolUse hook, `guard-criteria-evidence.sh`, denies a shell command that writes the `dotbabel-criteria` marker outside the `dotbabel-criteria` bin. The hook stops the direct route. A local agent with the owner's credentials can still reach GitHub through a script, so level 1 carries the same residual risk as a local-attest attestation (R-19). At level 2, set with `criteria.require_ci_check: true`, the gate also requires the `dotbabel criteria` CI check from the `test.yml` template to succeed on the head SHA. CI runs the repository's code at that SHA in GitHub's environment, which a local agent cannot forge. Level 2 costs CI minutes, so it is opt-in.
