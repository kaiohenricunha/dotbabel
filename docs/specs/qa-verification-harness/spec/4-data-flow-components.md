# §4 — Data Flow / Components

> Current state analysis + target architecture.

## Current State

[current-state/analysis.md](../current-state/analysis.md) holds the grounded audit (DOC-2). In short: specs carry commands but no criteria, and the pull request stage runs tests but checks only the test plan that the author wrote. The quality layer cannot trigger a tool by path, and `critical_paths` is parsed but unused. Nothing checks the deployed system beyond commit SHAs and the npm registry.

## Shared State

- **The evidence comment** is the only state shared between verification and the merge gate. Its marker names the head SHA, so a new push makes it stale without a clean-up step (REL-2).
- **`spec.json`** is shared by authoring, validation, verification, and the gate, which asks whether any linked spec declares criteria.
- **`.dotbabel.json`** is shared by quality runs, the criteria command, and the gate.
- **The trust allowlist** is user scope. Every component reads it, and none writes it.
- **Synchronization** needs nothing beyond Git and GitHub, because every run reads fresh state. When two verification runs on one pull request edit the same comment, the last writer wins, and the gate still compares the SHA inside the payload.

## Target Architecture

### Flow 1 — Criteria-first authoring

1. The `spec` skill writes `acceptance_criteria` for each work unit into `spec.json`, and each §6.3 prompt lists the same test names (KD-1).
2. `dotbabel-validate-specs` checks only the shape (Q-5).
3. The `validate-spec` audit reports a spec with no criteria as an INFO finding, and its Phase 4 runs `dotbabel criteria verify --spec <id>`.

### Flow 2 — Verification inside `review-pr`

1. `review-pr` finishes its last push at step 7 (`skills/review-pr/SKILL.md:164`).
2. At step 11 (`skills/review-pr/SKILL.md:210`), `review-pr` runs `dotbabel criteria verify --pr <N> --post`.
3. The command reads the `## Spec ID` section with `extractTemplateSection` (`plugins/dotbabel/src/spec-harness-lib.mjs:333`) and loads each listed spec. It exits 0 with a notice when no listed spec declares criteria.
4. For each criterion, the command checks that every named test file exists and contains the test name, runs `argv` through the quality runner, and confirms each test (KD-3).
5. The command redacts and truncates the output, builds the payload, and creates or edits the evidence comment pinned to the head SHA (KD-2).
6. `review-pr` reads each named test and opens a review thread for any test that asserts nothing or mirrors the implementation (KD-4). It fixes or answers each thread before step 12 resolves it.
7. If any criterion is not `pass`, `review-pr` reports `BLOCKED`, and the conductor stops before `local-attest` (REL-10).

### Flow 3 — Merge gate

1. `dotbabel pr-stack gate --gate merge` fetches the body, files, mergeability, head SHA, and all comments.
2. It resolves the Spec IDs and sets `criteriaRequired` when any linked spec declares criteria.
3. `checkMergeGate` evaluates the existing reasons and, when `criteriaRequired` is true, the criteria reasons in §5.
4. When `criteria.enforcement` is `warn`, criteria reasons appear under `warnings`, and `ok` ignores them (KD-14).

### Flow 4 — Quality diff run

1. The scope step resolves the changed files.
2. The planner drops a tool whose `paths` match no changed file, unless `--all` is set, and records `not_triggered` (KD-5).
3. When a changed file matches `critical_paths`, the planner adds the test plan of every component in every profile and ignores `--path` narrowing for those plans (KD-6).
4. The `deep` profile adds detected mutation tools, and the parsers score only mutants on changed lines (KD-7).

### Flow 5 — Post-deploy

1. `release-conductor verify` runs its three registry checks (`skills/release-conductor/SKILL.md:225-249`).
2. When a deploy target exists, it runs `deploy-ops.mjs status` and then `deploy-ops.mjs smoke`. Otherwise it reports both as `SKIPPED`.
3. Any drift or failed smoke check makes the verdict FAIL. The skill then recommends `/rollback-prod` and stops (KD-13).

### Flow 6 — Local hooks

1. The pre-push hook runs `dotbabel quality check --profile fast` against the merge base with the upstream branch (KD-11). A critical-path change adds tests to that run (KD-6).
2. With `CHECK_ON_STOP_TESTS=1` in a trusted repository, `check-on-stop.sh` runs the related tests for files changed in the turn (KD-12).

### Key Decisions

<!-- Tag each as KD-N for cross-referencing -->

- **KD-1 — Acceptance criterion shape. Decided 2026-09-11.** A criterion has an id, separate `given`, `when`, and `then` statements, the tests that prove it as a file path plus a test name, and one `argv` command that runs those tests. Two existing conventions set this shape. Specs already list TDD tests as a file followed by test names (`docs/specs/cli-bootstrap-command/spec/6-implementation-plan.md:51-57`), and quality tools already declare commands as `argv` arrays with no shell strings (`docs/quality.md:175`). The repository owns the command, so dotbabel never guesses how a test runner filters tests. The validator checks only the shape, because a spec exists before its tests do. At verification time, dotbabel checks that each named test appears in its file, runs the command, and records the exit code and the output tail. §5 holds the schema.
- **KD-2 — One trusted, SHA-pinned evidence comment. Decided 2026-09-11.** The owner delegated this choice, and the recommended option was adopted. The evidence lives in one pull request comment. Its first line is exactly `<!-- dotbabel-criteria verified-sha=<head SHA> -->`, its second line carries the payload, and a readable table for people follows. The merge gate reads only the two marker lines. It accepts a comment only when the author association is in `criteria.trusted_associations`, whose default `["OWNER"]` matches local-attest (`skills/local-attest/SKILL.md:210`). The command edits its earlier comment instead of adding a new one. The marker helpers in `plugins/dotbabel/src/local-attest-lib.mjs:47-110` move into a shared module, and the local-attest marker text stays unchanged. The pull request body was rejected because anyone who can edit it can forge the evidence (A-6). Commit statuses and check runs were rejected in A-7.
- **KD-3 — A pass needs confirmed tests, not only exit code 0. Decided 2026-09-11.** A criterion may declare an optional `report` with format `junit-xml` and a repository-relative path. A criterion passes only when its command exits 0 and each named test is confirmed. With a report, a testcase confirms a test when its name equals the test name, or ends with it after `>`, `::`, `.`, or `/`, and when it has no `failure`, `error`, or `skipped` child. Without a report, the test name must appear in the command output. Exit code 0 with a missing name makes the criterion `unconfirmed`. This closes the zero-test false pass, where a filter that matches nothing still exits 0, as `go test -run` does. JUnit XML is the de facto format for per-test results (DOC-15).
- **KD-4 — Deterministic gates, advisory AI judgment. Decided 2026-09-11.** Merge-gate verdicts come only from evidence that commands produce and from deterministic quality metrics. The review agent's test-quality judgment opens review threads, which `review-pr` must fix or answer before it resolves them. The agent never writes a criterion status. When the repository configures a mutation tool, the mutation score is the deterministic backstop. Model output varies between runs and can be steered by instructions hidden in the content it reads (DOC-17), so it informs a gate and never decides one.
- **KD-5 — Path-triggered tools and the `regression` capability. Decided 2026-09-11.** Any configured quality tool may declare `paths`, an array of repository-relative globs. With `paths`, the planner keeps the tool only when a changed file matches, or when `--all` is set. Otherwise the result state is `not_triggered` with verdict `info`. A new `regression` capability runs in `pr` and `deep` and feeds a new hard rule, `correctness.regression`. Like `correctness.tests`, the rule accepts no exception and no baseline. This replaces `regression_paths` (Q-2): the repository owns the check, and dotbabel decides when it runs and records its verdict.
- **KD-6 — `critical_paths` requires the full suite. Decided 2026-09-11.** When a changed file matches `critical_paths` (`plugins/dotbabel/src/quality/config.mjs:15`, `:90`, `:191`), the planner adds the test plan of every component in every profile, `fast` included. It also ignores `--path` narrowing for those plans, and the envelope lists the matched files in `critical_matches`. Without a `--path` filter, the `pr` and `deep` profiles already run whole-component test commands (`plugins/dotbabel/src/quality/discovery.mjs:112-116`). The escalation therefore matters where the scope is narrow: the `fast` profile in the pre-push hook, and `--path` runs. The rule-floor line at `CLAUDE.md:50` changes to name `critical_paths`.
- **KD-7 — Detect configured mutation tools and score changed lines. Decided 2026-09-11.** Adapters detect a mutation tool only from repository configuration: a Stryker configuration file for JavaScript and TypeScript, mutmut configuration in `pyproject.toml` or `setup.cfg` for Python, and a Gremlins configuration file for Go. P-C4 confirms each file name against the tool's documentation. The plans run only in `deep`. Parsers read per-mutant results and compute the score as detected ÷ valid × 100 for mutants that start on a changed line (DOC-16). Detected means killed or timed out, and valid means detected, survived, or with no coverage. With no mutant on a changed line, the rule reports `not_applicable`. The current `stryker-json` parser reads only a top-level score (`plugins/dotbabel/src/quality/reports.mjs:114-117`), so P-C4 replaces it and checks the result against a real captured report.
- **KD-8 — Built-in Python and Node plans for declared tools. Decided 2026-09-11.** For Python, plan `pytest` when the component declares pytest configuration: `[tool.pytest.ini_options]` in `pyproject.toml`, a `pytest.ini` file, `[pytest]` in `tox.ini`, `[tool:pytest]` in `setup.cfg`, or a root `conftest.py`. Run it under `uv run` or `poetry run` when the matching lockfile exists (`docs/quality.md:101`). Plan coverage as `pytest --cov --cov-report=json:<path>`, parsed as `coveragepy-json`, only when `pytest-cov` is a declared dependency. For Node, when no coverage script exists, plan `vitest run --coverage` with the JSON reporter when a Vitest coverage provider is a declared dev dependency. Plan `jest --coverage` with the JSON reporter when Jest is declared. Both reports parse as `istanbul-json`. A repository script or Make target keeps priority (`plugins/dotbabel/src/quality/adapters/node-tools.mjs:36-45`).
- **KD-9 — Remove `regression_paths` and `verification_commands`. Decided 2026-09-10.** Delete both keys from `docs/repo-facts.json:38`, `plugins/dotbabel/templates/docs/repo-facts.json:16-17`, and `examples/minimal-consumer/docs/repo-facts.json:16`. Rewrite `CLAUDE.md:50` and regenerate the host instruction files. Replace step 5 of `commands/merge-pr.md:59-67`, its template copy, and `.github/prompts/merge-pr.prompt.md` with the quality verdict. `dotbabel doctor` warns when a repository still gives either key a value, and it names the replacements (OPS-6).
- **KD-10 — Consumer CI templates verify but never post evidence. Decided 2026-09-11.** `test.yml` runs on `pull_request`. A classify job honors a trusted local-attest marker for the head SHA and fails closed, as this repository's `.github/workflows/test.yml` does. When the job finds no marker, a verify job runs `dotbabel quality check --profile pr` and, when the pull request names a spec with criteria, `dotbabel criteria verify --pr <N>`. The job then uploads both JSON reports. `quality.yml` runs the `deep` profile weekly and on manual dispatch, following `.github/workflows/quality.yml`. CI never posts the evidence comment. Its bot identity is not a trusted association by default, and a second writer would race the local run. The CI report is an independent re-run that a reviewer can compare. Both templates meet SEC-7, and they mark their language setup steps for consumers to edit.
- **KD-11 — An opt-in pre-push hook that never traps a push. Decided 2026-09-11.** `githooks/pre-push` runs `dotbabel quality check --profile fast` against the merge base with the upstream branch. Quality exit 1 blocks the push. Exit 2, a timeout, or a missing `dotbabel` prints a notice and allows the push. `BYPASS_PRE_PUSH=1` and `git push --no-verify` skip the hook. Activation stays manual with `git config core.hooksPath githooks`, because the hook runs repository code, and the docs say so next to that command.
- **KD-12 — Related tests at turn end, opt-in and trusted only. Decided 2026-09-11.** `check-on-stop.sh` gains a tests stage that runs only with `CHECK_ON_STOP_TESTS=1` in a trusted repository. It uses each runner's own scoping, as `review-pr` already does (`skills/review-pr/SKILL.md:132`): `vitest related --run`, `jest --findRelatedTests`, `go test` on touched packages, and `pytest` on touched test files. `CHECK_ON_STOP_TIMEOUT` bounds the stage (`plugins/dotbabel/hooks/check-on-stop.sh:78`), and the give-up counter still stops after two blocks (`:80`).
- **KD-13 — Smoke checks live with the deploy targets. Decided 2026-09-11.** Each target in `.claude/deploy-targets.json` (`skills/deploy-status/scripts/deploy-ops.mjs:143-155`) may declare a `smoke` array. `deploy-ops.mjs smoke` runs `http` checks, which use GET only, and `command` checks, which use `argv`. The helper stays self-contained, because scaffolded copies cannot import package source, so it carries its own guards for URLs, the environment, redaction, and time. The `smoke-test` skill wraps the command. `release-conductor verify` adds deploy status and smoke results when a target exists. On a failure, it recommends `/rollback-prod` and stops, because the rule floor forbids production changes without explicit instruction.
- **KD-14 — Enforcement, trust, and timeout settings. Decided 2026-09-11.** `.dotbabel.json` gains a `criteria` object with three keys. `enforcement` is `block` by default, or `warn`. `trusted_associations` defaults to `["OWNER"]`. `timeout_seconds` defaults to 600 and accepts 1 through 3600, the quality tool bounds in `plugins/dotbabel/src/quality/config.mjs:67-68`. The project config loader (`plugins/dotbabel/src/project-sync.mjs:104`) and `schemas/dotbabel.config.schema.json` validate the object. `warn` is the documented rollback switch in §6.6, and a switch to `warn` shows up in the diff of a committed file.
