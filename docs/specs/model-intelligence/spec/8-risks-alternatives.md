# §8 — Risks and Alternatives

> Known risks with mitigations, rejected approaches with reasoning.

**Settled.** The owner decided the risk register and the rejected alternatives on 2026-09-18. Ratings describe the risk before the mitigations in this specification are fully deployed. Likelihood and impact use `Low`, `Medium`, and `High`.

### Risk interpretation

- **R-1 — Release baseline staleness.** Likelihood is Medium because provider/runtime model churn is expected and was directly observed during the investigation (DOC-2, finding 11). Impact is High because the affected path bypasses local dynamic resolution: a broken selector embedded in a shipped plugin/workflow can require a new Dotbabel package release. This risk cannot be removed completely while KD-3/KD-6 require deterministic release-time projection.
- **R-2 — Runtime parser/schema change.** Likelihood is Medium because these runtimes are actively evolving and their accepted artifact formats are not Dotbabel-owned. Impact is High because a parser rejection can make the generated artifact unusable rather than merely reducing recommendation quality. KD-5 deliberately avoids increasing this risk through private metadata leakage.
- **R-3 — Generated-copy edit loop.** Likelihood is High during migration because the change is intentional and user-visible: edits that were previously immediately reflected through symlinks will require regeneration. Impact is Medium because canonical state remains intact and drift is recoverable; the principal failure mode is stale or manually edited derived state rather than loss of policy.
- **R-4 — Knowledge-source uncertainty.** Likelihood is Medium until RQ-1 closes. Impact is Medium because the architecture does not require a knowledge source for local runtime operation. Losing such a source reduces global metadata quality/coverage rather than disabling Model Intelligence.
- **R-5 — Safety migration error.** Likelihood is Low because the specification introduces multiple independent safeguards before legacy metadata is removed. Impact is High because silently dropping a security/reliability floor would violate preserved behavior and could select materially weaker compute for safety-sensitive work. The low likelihood does not justify weakening the migration gates.
- **R-6 — Copilot cross-tree leakage.** Likelihood is High because DOC-2 already observed Copilot discovering skill trees outside the previously assumed target path. Impact is Medium because current evidence primarily shows discovery/topology leakage rather than proven unsafe model enforcement, but it can cause duplicate/wrong artifacts and invalidate projection assumptions. The likelihood drops substantially after KD-5 projection topology is fully deployed and covered by real-runtime tests.
- **R-7 — Mixed-generation projection.** Likelihood is Low after ARCH-62/ARCH-69 are implemented because the critical transaction is narrow and explicitly locked. Impact remains High because mixed generated state could make different artifacts enforce mutually inconsistent runtime configurations.

## Rejected Alternatives

- **A-1 (KD-1)** — Keep legacy `model:` / `effort:` as the canonical cross-runtime schema. **Rejected.** The existing keys encode runtime-specific mechanics rather than provider-neutral workload intent. They cannot safely express dynamic selection, semantic floors, binding scope, runtime-specific pinning without conflating runtime and vendor, or unsupported versus inherited behavior. They remain only as transitional compatibility projections (ARCH-19).
- **A-2 (KD-1)** — Put canonical Model Intelligence intent into generic runtime metadata. **Rejected.** Using generic runtime-owned metadata fields would make Dotbabel semantics depend on undocumented third-party extension behavior. Canonical intent therefore uses the Dotbabel-owned `dotbabel.compute` namespace.
- **A-3 (KD-2)** — Depend entirely on existing Claude symlink/direct-file behavior. **Rejected.** Claude's binding behavior differs across agents, commands, and skills (PB-10). A single direct-file strategy cannot simultaneously preserve agent model binding, command session-wide effects, inert skill model fields, private metadata stripping, and dynamic/floor semantics. Runtime-specific generated projections are required where transformation is necessary.
- **A-4 (KD-3)** — Resolve plugin baselines dynamically on the consumer machine. **Rejected.** Shipped plugin behavior would depend on current network access, current credentials, the current provider catalog, and consumer-specific discovery state. It would violate deterministic/offline package build (ARCH-39) and make the same package produce different shipped baseline behavior.
- **A-5 (KD-3)** — Hardcode a permanent Claude model directly in policy. **Rejected.** That would move volatile market state into permanent semantic policy and violate the principle "hardcode the decision framework, discover/download capability facts" (ARCH-15). The concrete release selector belongs to the versioned release snapshot/projection.
- **A-6 (KD-5)** — Leave `dotbabel.compute` in all shared runtime-visible skill trees and rely on runtimes ignoring it. **Rejected.** Unknown-key tolerance is not a stable API. Generated copies strip Dotbabel-private metadata unless a runtime explicitly verifies it as safe (ARCH-45).
- **A-7 (KD-5)** — Store canonical Model Intelligence semantics in each runtime's generic metadata field. **Rejected.** This would fragment the semantic source of truth and couple Dotbabel's domain model to runtime-specific metadata conventions.
- **A-8 (KD-6)** — Let `ai-review` use the Claude CLI default model. **Rejected.** The result would depend on mutable runtime defaults outside Dotbabel's policy and could change without a repository or package diff.
- **A-9 (KD-6)** — Perform live discovery/resolution inside CI before every `ai-review`. **Rejected.** This would introduce mutable network/runtime dependencies into a workflow that should be reproducible from the released package (ARCH-35, TEST-1). The workflow therefore uses a release-time projected explicit session configuration.
