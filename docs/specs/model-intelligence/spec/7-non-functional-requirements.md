## Performance

Decided by the owner on 2026-09-18. Performance requirements apply only to deterministic local Model Intelligence work. Network discovery, authenticated provider APIs, and external runtime execution are excluded from wall-clock performance thresholds because their latency is not controlled by Dotbabel.

- **PERF-1**: Resolver latency. For a warmed Node process, resolving one artifact against a fixture catalog containing at least 500 model/configuration records across all six runtime ids completes with p95 <= 10 ms. On breach, the Tier 1 resolver performance test fails, and the change is optimized or the threshold is deliberately revised in the spec with evidence before merge.
  - Measurement: discard an initial warm-up set; execute at least 1,000 `resolve()` calls; use deterministic in-memory requirement, policy, catalog, runtime-contract, and observation fixtures; include explanation, diagnostics, confidence, and enforcement calculation in the measured operation; exclude fixture loading and Node process startup.
  - This converts the quality claim of the earlier spec, "adds no measurable latency" (`docs/specs/dotbabel-agents/spec/7-non-functional-requirements.md:9`), into a concrete hot-path limit.
- **PERF-2**: Project-sync latency. On the repository's fixed Model Intelligence sync fixture, a complete `dotbabel project-sync` completes with p95 <= 1.5 seconds over at least 10 warmed runs on the Tier 1 CI environment. On breach, the Tier 1 project-sync performance test fails; an implementation that misses the threshold cannot be merged merely because functional tests pass.
  - Conditions: capability evidence already cached; no source refresh; no provider/network access; no runtime/model execution; generated projections requiring normal manifest/hash/drift processing.
  - The fixture includes enough artifacts to exercise the normal Dotbabel projection path, including agents, commands, and skills, rather than an empty/minimal no-op tree.
  - The requirement is not defined as a percentage of the pre-Model-Intelligence implementation. The legacy implementation is intentionally removed during migration and is not a permanent benchmark oracle.
- **PERF-3**: Deterministic release-build overhead. For the committed repository state, snapshot load + snapshot validation + release-time resolution + Model Intelligence projection generation/checking adds no more than 1.0 second to one `build-plugin --check` execution in the Tier 1 performance fixture. On breach, the Tier 1 release-projection performance test fails.
  - Measurement excludes the pre-existing non-Model-Intelligence build work and excludes process startup where the harness can isolate the Model Intelligence phase directly.
  - The requirement applies to consumption of the committed snapshot, not to `dotbabel models snapshot --write` when that command performs external source discovery. External snapshot refresh latency is governed by source availability/timeouts rather than a package-build performance SLO.
- **PERF-4**: No performance SLO exists for external refresh. There is intentionally no statement such as `snapshot refresh <= N seconds` or `models refresh <= N seconds` for network/runtime-backed discovery. Those operations require bounded adapter timeouts and explicit `unavailable`/`unknown` outcomes under the reliability requirements. This keeps provider or runtime latency from making deterministic Dotbabel CI flaky.

## Reliability

Decided by the owner on 2026-09-18. Reliability requirements preserve Dotbabel's existing operation when Model Intelligence dependencies are unavailable and prevent transient discovery failures from becoming durable state.

- **REL-1**: Bounded adapter operations. Every source-adapter operation has a finite timeout: 10 seconds by default for a local/subprocess operation and 20 seconds for a network operation. On breach, the adapter contract/integration test fails, and the adapter is not eligible to declare that operation `supported` until bounded termination is restored.
  - An adapter may declare a more appropriate operation-specific timeout when empirical runtime behavior requires it, but it remains finite and explicit. No adapter operation inherits an unbounded subprocess or HTTP timeout.
  - On timeout: `AdapterResult.status = unavailable`, `diagnostic.code = timeout`, `diagnostic.retryable = true`, unless the operation contract has stronger evidence supporting another non-success state.
  - A timeout never hangs the caller indefinitely, is never converted to `ok`, never replaces a previously valid cache entry, and never silently produces an empty capability catalog.
  - The default thresholds apply to one adapter operation, not an entire multi-source refresh. Independent source operations may be orchestrated concurrently where safe (PERF-4).
- **REL-2**: Failed refresh preservation. A failed, empty, malformed, timed-out, older, or otherwise unusable refresh never replaces a valid cache entry. This is an invariant: existing cache valid + candidate refresh unusable → the existing cache remains byte-for-byte usable, and the caller receives the refresh diagnostic separately from the retained cached evidence. On breach, the Tier 1 cache/property tests fail and the change cannot merge. This carries ARCH-30 into the reliability contract (TEST-7).
- **REL-3**: Conservative stale-lock recovery. A lock is not eligible for automatic stale recovery until it is at least 10 minutes old, and age alone is never proof that a lock is stale. On breach, the lock/concurrency tests fail, and automatic stale-lock removal is disabled for that path until conservative ownership verification is restored. This realizes ARCH-65.
  - For a lock containing the pid, the process-start identity when available, the host/process environment identity, and the resource: age under 10 minutes → never auto-remove; age of 10 minutes or more + same host/environment + owner pid proven dead → eligible for recovery; age of 10 minutes or more + pid exists + recorded process-start identity differs → eligible, because the pid was reused; age of 10 minutes or more + owner liveness cannot be established safely → do not auto-remove.
  - Where the platform does not provide a reliable process-start identity, pid liveness may establish that a process is still alive, but pid absence is the minimum evidence required for automatic recovery.
  - For a lock created on another host/environment, or where ownership metadata is insufficient, the result is "lock unavailable / manual recovery required" rather than automatic deletion.
- **REL-4**: Default evidence freshness. When a source adapter declares no source-specific freshness policy, evidence is stale after 6 hours and expired after 24 hours for runtime discovery and for official provider model APIs; stale after 15 minutes and expired after 1 hour for runtime/session observation; and stale after 24 hours and expired after 7 days for Models.dev or an equivalent broad catalog. On breach, the freshness contract tests fail, and the affected evidence is treated as `unknown` or expired rather than silently accepted.
  - The states: `age <= stale threshold` → fresh; `stale threshold < age <= expiry threshold` → stale; `age > expiry threshold` → expired. `unknown` remains available when no valid observation timestamp exists.
  - Runtime discovery (installed/selectable models, supported reasoning levels, runtime capability enumeration) uses 6h/24h because installed versions, accounts, configuration, or entitlements may change within a working day.
  - Runtime/session observation (currently active model, current effective reasoning configuration, session-level selector) uses 15m/1h because the active runtime/session can change independently of the capability catalog. A stale observation is never presented as proof of the current active configuration without an explicit stale qualifier.
  - Official provider APIs use 6h/24h: provider catalogs can change quickly, but provider availability does not justify making every resolver call depend on live network access.
  - Broad catalog sources use 24h/7d: they are lower-frequency global knowledge rather than authoritative evidence of the current user's local invokability.
  - Override rules: a source-specific policy may shorten or lengthen these windows only when the adapter documents why, and the effective policy and provenance expose that override. No adapter represents `expired` as `fresh` simply because refresh failed.

The REL-4 default windows:

| Evidence class                                          |      Fresh after | Stale until | Expired after |
| ------------------------------------------------------- | ---------------: | ----------: | ------------: |
| Runtime discovery / installed-model capability evidence | observation time |     6 hours |      24 hours |
| Runtime/session observation                             | observation time |  15 minutes |        1 hour |
| Official provider model API                             | observation time |     6 hours |      24 hours |
| Models.dev or equivalent broad catalog                  | observation time |    24 hours |        7 days |

- **REL-5**: Offline independence. With the network unavailable and the Model Intelligence cache empty, every existing Dotbabel operation that does not require Model Intelligence remains functional with its existing semantics. This is an invariant. On breach, the offline regression suite fails and the change cannot merge. This realizes ARCH-27 and ARCH-34.
  - Examples include unrelated validators, quality commands, repository tooling, and artifact operations whose behavior does not depend on model selection. Model Intelligence initialization is not a mandatory startup dependency for the package.
  - A command outside the Model Intelligence dependency boundary does not fail merely because Anthropic, OpenAI, or Models.dev is unreachable, no runtime model catalog can be discovered, or the Model Intelligence cache does not exist.
- **REL-6**: Provider churn does not require a Dotbabel release. In the provider-churn fixture, adding or removing a discoverable model without changing schema/runtime semantics requires 0 Dotbabel source-code changes and 0 package releases for local dynamic resolution to adapt. On breach, the architecture/acceptance test fails; provider-specific market state has leaked into permanent policy or implementation and is removed. This carries ARCH-36 into §7.
  - A provider model addition, removal, rename, or capability change does not require a new Dotbabel package release unless the change invalidates a committed release-time projection or runtime contract. Normal provider churn is absorbed through discovery/refresh → capability cache → resolver, without changing shipped semantic policy.
  - The explicit bounded exception is KD-3/KD-6 release projection data, where a retired shipped selector may require a corrective snapshot/package release.
- **REL-7**: Active reliability does not regress. For deterministic Model Intelligence operations using valid local inputs (`resolve`, `status`, local cache read, projection drift check), the Tier 1 suite completes 100% of valid fixture cases without an uncaught exception, a partial canonical write, or a silent fallback. On breach, the Tier 1 reliability tests fail and the change cannot merge. Expected conflicts, unavailable sources, unknown evidence, and policy failures are structured results rather than reliability failures. This is the measurable §7 counterpart of the reliability quality claim in §1 `Why Now` and §2.

## Operational

Decided by the owner on 2026-09-18.

- **OPS-1**: Release snapshot age. `dotbabel models snapshot --check` and `dotbabel models status --check` fail when a required release projection depends on evidence older than 7 days. On breach, refresh the release evidence with `dotbabel models snapshot --write`, review the resulting diff and provenance, and rerun `snapshot --check` before release.
  - `dotbabel models status` reports the age of the committed release snapshot and the age of the evidence that backs each release projection. The snapshot has no `generatedAt` (ARCH-71), so its operational age is derived from its required source evidence: `releaseSnapshotAge` is the maximum age, by `observedAt`, of any required evidence record used by a shipped release projection. Optional evidence that does not participate in a shipped projection does not make the release snapshot stale.
  - Informational `dotbabel models status` still exits successfully and reports the age/staleness without mutating anything.
  - This threshold is a release gate, not an expiration rule for an already-published package. A package installed months later remains reproducible from its committed snapshot and reports its age rather than becoming unusable (ARCH-43, ARCH-72).
- **OPS-2**: Capability cache size. The Model Intelligence capability-cache root has a maximum total size of 64 MiB, and one cache entry has a maximum size of 8 MiB. On breach, the oversized candidate is not committed, or reconstructible obsolete cache entries are evicted until the cache is within the limit; `status --check` fails if the cache remains above 64 MiB after maintenance.
  - `dotbabel models status` reports the total cache size, the entry count, and the size of each source/runtime cache entry where useful. A normal refresh does not leave the cache tree above 64 MiB after cache maintenance completes.
  - Because all capability-cache data is reconstructible (ARCH-22), maintenance may evict obsolete entries using an operational recency policy. Eviction never removes canonical artifacts, user/project configuration, the committed release snapshot, or generated projection manifests outside the cache tree.
  - If one candidate cache entry alone exceeds 8 MiB, the adapter rejects or reduces that candidate rather than allowing one source to consume the entire cache budget.
  - A failed size check never deletes the last valid evidence needed merely to make the number smaller; availability and the ARCH-30 preservation rules still apply. The bound also serves the disk-hygiene rule of the rule floor: the WSL disk on the owner's machine only grows.
- **OPS-3**: Stable machine-readable diagnostics. Every Model Intelligence error, warning, conflict, unavailable state, and check failure exposed through the CLI has a machine-readable diagnostic code, and within one published major/minor release line a patch release keeps the documented meaning of every existing diagnostic code and every existing `--json` field. On breach, the contract tests fail and the incompatible JSON/diagnostic change cannot ship as an ordinary patch release.
  - Human-readable text is not the API. A patch release may add a new diagnostic code, improve human-readable wording, and add optional JSON fields. It does not silently repurpose an existing code to mean a different condition.
  - Removing a field, changing its type, or changing a diagnostic code's meaning requires an intentional compatibility/version decision rather than an incidental patch.
- **OPS-4**: Credential and identity redaction. Model Intelligence logs, diagnostics, manifests, status output, JSON output, cache metadata exposed to users, and test failure reports contain 0 credentials, 0 authentication tokens, 0 secret API keys, 0 refresh/access tokens, and 0 account identifiers obtained from runtime authentication state. On breach, the redaction/security test fails, affected output is treated as a security defect, and the change cannot ship until the secret-bearing path is removed.
  - Adapters may report abstract authentication states such as `authenticated`, `auth_required`, and `auth_unavailable`, but never expose the credential or account identity used to establish that state.
  - Command lines or subprocess environments containing secrets are redacted before they enter diagnostics. The existing criteria evidence redaction (`plugins/dotbabel/src/criteria/`, AC-16 of the QA harness spec) is the in-repo precedent.
  - Structured provenance records may identify the runtime/source id, the runtime/source version, the evidence kind, timestamps, and model identifiers, but not user credentials or provider account ids.

## Security

Decided by the owner on 2026-09-18. Model Intelligence may inspect runtimes, read external capability evidence, and generate runtime-specific artifacts, but it does not gain authority over runtime credentials, provider accounts, arbitrary repository execution, or arbitrary filesystem paths.

- **SEC-1**: Runtime and credential ownership boundary. Source adapters never mutate runtime configuration roots, runtime credential stores, provider account configuration, or provider authentication state (§2, `Does Not Mutate`). On breach, security tests fail, and the adapter capability is treated as unsupported until the mutating path is removed.
  - Runtime discovery and observation use read-only or isolated configuration where the runtime supports it.
  - An adapter may use an already-existing runtime/provider credential only when its descriptor explicitly declares authenticated access under the §5 adapter contract (`auth: optional-existing | required-existing`).
  - Model Intelligence never creates a provider credential, rotates one, copies one into Dotbabel config/cache, changes the runtime's authenticated account, or writes authentication material into a runtime configuration root.
  - An explicitly requested observation that requires a model invocation may incur ordinary provider usage, as the adapter contract establishes, but it does not grant Model Intelligence administrative authority over the provider account.
- **SEC-2**: Projection path confinement. `materialize/` writes only to Dotbabel-owned projection targets derived from the projection plan and recorded in the projection manifest, and every destination resolves inside its expected owning root before any write. On breach, the write is refused before mutation, the security/path-confinement test fails, and no partial projection transaction is committed.
  - Owning roots are the project root, the configured Dotbabel/runtime projection root, and a `configDir()`-owned Dotbabel path.
  - The materializer rejects `..` traversal escaping the owning root; absolute-path injection from artifact metadata; symlink traversal that resolves outside the owning root; manifest entries targeting arbitrary external paths; and replacement of files not proven Dotbabel-owned unless an explicit migration/force contract permits it.
  - For protected repository paths such as `.claude/**`, Model Intelligence does not bypass existing repository governance merely because the file is generated. Writes to such paths occur only through the explicit projection/sync/materialization workflow and remain subject to the existing protected-path checks (`docs/repo-facts.json`).
- **SEC-3**: External source isolation. Knowledge-source and provider-source adapters treat remote responses strictly as data, network source URLs use HTTPS except for explicitly injected local test fixtures, and public sources receive 0 Dotbabel credentials. On breach, the source result is rejected, and the adapter is not considered safely usable until transport, credential handling, or content isolation is corrected.
  - Remote content is never evaluated as JavaScript, sourced as shell, interpreted as Dotbabel instructions, executed as a command, or imported dynamically as trusted code.
  - Authenticated official-provider sources may receive only the credential required by that adapter and only through the existing authorized credential mechanism. Model Intelligence never persists that credential into the capability cache, the release snapshot, a projection manifest, diagnostic output, or logs (OPS-4).
  - Remote response bodies are subject to bounded-response handling: a source candidate that would produce a cache entry above the OPS-2 8 MiB per-entry limit is rejected or reduced before persistence, and the REL-1 20-second network timeout applies.
- **SEC-4**: Generated output is never canonical input. A generated runtime artifact whose current content does not match its recorded `outputHash` is drift, and Dotbabel never reads modified generated output back into canonical `dotbabel.compute`, shipped policy, user/project policy, the release snapshot, or resolver constraints. On breach, drift/canonical-authority tests fail, and automatic materialization stops rather than adopting the generated file as policy. This carries ARCH-52 into the security contract.
  - The direction of authority remains canonical source + policy + capability evidence → resolver → generated projection, never edited generated projection → canonical policy.
  - Recovery of useful manual edits requires an explicit human action to move those edits into the canonical source before regeneration.
- **SEC-5**: Release snapshot integrity and reviewability. The committed release capability snapshot is reviewed source-controlled content: every change appears as an ordinary pull-request diff, passes schema validation, has a `snapshotId` matching its deterministic projection-relevant content, passes `dotbabel models snapshot --check`, and remains reproducible without network access during the package build. On breach, snapshot/build validation fails and the release cannot proceed.
  - A snapshot whose declared `snapshotId` differs from the computed `snapshotId` is rejected. Build tooling never silently rewrites an invalid snapshot merely to make the check pass.
  - Updating the snapshot is an explicit `dotbabel models snapshot --write` operation followed by normal code review (ARCH-64).
- **SEC-6**: Repository trust boundary. A Model Intelligence operation that would execute a command derived from repository-controlled configuration requires either that the exact repository path is trusted or an explicit existing execution override intended for controlled automation, such as `--allow-project-commands`, where the owning subsystem already supports that override. On breach, trust-boundary tests fail, and the command does not execute until the existing repository trust requirement is satisfied.
  - Model Intelligence never automatically adds a repository to the trust allowlist (`plugins/dotbabel/src/trust-allowlist.mjs`), weakens an existing trust decision, infers trust from the presence of `.dotbabel.json`, `.claude/**`, or a projection manifest, treats generated status/provenance as proof of repository trust, or executes a project-controlled command merely because an adapter declares `requiresTrust`.
  - If required trust is absent, an operation requiring project execution returns a structured trust-required/unavailable result and executes no command. Operations that do not require project execution remain usable. A fresh repository with no trust allowlist therefore behaves as today: automatic project-command execution is disabled, and read-only/non-project-executing Dotbabel functionality remains available.
  - For hook-driven paths such as `check-on-stop`, Model Intelligence inherits the same trust decision rather than creating a second trust database or allowlist.
