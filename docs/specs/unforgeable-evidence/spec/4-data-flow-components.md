## Sign path

1. The writer builds the payload as today, plus `scope: { repo, pr, family }`. Each payload already has `head_sha`.
2. The writer renders line 2.
3. If a key is configured, the writer prints the head SHA, the family, and the verdict. Then it runs `<absolute path>/ssh-keygen -Y sign -n dotbabel-evidence@v1 -f <key>` with line 2 on stdin. For a security key, the human touches the key now. The summary comes from a process the agent controls, so it helps an honest run and protects nothing against a dishonest one (KD-5, §8 R-1).
4. The writer appends line 3: `<!-- dotbabel-evidence-signature v1 <base64url of the armored SSHSIG> -->`.
5. The writer posts the comment as today.

## Verify path

1. The gate resolves the trust ref and probes it (§5.2). It reads the `evidence` block and the signers file with `git --no-replace-objects show <trust ref>:<path>`, in a cleaned environment (ARCH-7).
2. If the trust ref requires no signature for the family and the selected comment has no line 3, the ladder runs exactly as today (ARCH-3, REL-2).
3. The gate keeps the namespace-pinned signer lines (§5.4), resolves `ssh-keygen` by an absolute path, and runs the capability probe once for each process (REL-1).
4. For each current comment, newest first, the gate writes the line-2 bytes, the signature, and the kept signer lines to a private temporary directory (REL-3). `ssh-keygen -Y find-principals` names the principal. The gate fails closed on zero principals, several principals, or a wildcard. `ssh-keygen -Y verify -I <principal> -n dotbabel-evidence@v1` gets line 2 on stdin through the `input` option.
5. The gate parses the SSHSIG blob and checks the security-key flags (KD-11).
6. The gate compares the signed scope and `head_sha` with the pull request (KD-3).
7. The first comment that passes is the selected comment. The existing rungs continue: payload, then the family rungs (§5.7).
8. Merge gate only: the gate computes the trust-root change (§5.3). If there is one, it runs steps 3 to 6 on the current `trust-root` comments, and it compares their `changes` with its own result.

## Separate-user signer (optional tier, KD-6)

1. The agent writes a request `{repo, pr, head_sha}` to a spool directory that the signer user can read.
2. The signer, a systemd unit of user `dotbabel-signer`, fetches `head_sha` from the remote into its own checkout. It never reads the agent's worktree.
3. The signer runs the governed matrix from the base-ref configuration, in a sandbox with no read access to the key (SEC-3).
4. The signer signs, and writes the comment body to an outbox. The owner's session posts it. The poster must still be in `trusted_associations`, because the trusted-association rung stays (ARCH-4). A separate bot account needs that list widened on purpose.
5. The signer's code is a pinned install that the signer user owns. It is never the npm-linked development checkout that the agent can edit.
6. The signer's principal is in `evidence.unattended_principals`, because its key is not a security key (§5.1).
