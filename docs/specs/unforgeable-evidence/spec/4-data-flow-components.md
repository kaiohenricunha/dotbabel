## Sign path

1. Each family writer builds its payload as today, plus `scope: { repo, pr, family }`. Each payload already has `head_sha`. The writer renders line 2 and posts lines 1 and 2, unsigned, as today. It needs no key.
2. When the pull request changes the trust root, `dotbabel evidence trust-root --pr <N>` posts the trust-root comment the same way (§5.3).
3. After the last writer for the head, `dotbabel evidence bundle --pr <N>` reads the comments of the pull request. For each family, it takes the newest current comment: a trusted association, no edit, a line-1 marker that names the head, and a line 2 that decodes and carries a `scope` that matches. It names only payloads that carry `scope`, so a comment from an old writer stays unnamed (§8 R-6).
4. The bundle step computes `payload_sha256` over each selected line 2 (KD-2), and renders the bundle payload as its own line 2 (§5.6).
5. The bundle step prints the head SHA, and, for each family it names, the verdict and the hash. It prints the trust-root change too, when there is one. Then it runs `<absolute path>/ssh-keygen -Y sign -n dotbabel-evidence@v1 -f <key>` with the bundle line 2 on stdin. For a security key, the human touches the key now. For an approval agent, the human approves the dialog now. The summary comes from a process the agent controls, so it helps an honest run and protects nothing against a dishonest one (KD-5, §8 R-1).
6. The bundle step appends line 3: `<!-- dotbabel-evidence-signature v1 <base64url of the armored SSHSIG> -->`, and posts the bundle comment.

**A family comment re-posted after the bundle.** A re-post whose line 2 differs has a hash that the bundle does not name. It is unsigned until a new bundle names it, and that new bundle costs one more touch. A re-post whose line 2 is byte-identical has the same hash, so the bundle still covers it. With the switch on, the gate still judges older current comments, so an older comment that a verified bundle names can still be the selected comment (§5.7, §8 R-9).

## Verify path

1. The gate resolves the trust ref and probes it (§5.2). It reads the `evidence` block and the signers file with `git --no-replace-objects show <trust ref>:<path>`, in a cleaned environment (ARCH-7).
2. If the trust ref requires no signature for the family and no current bundle names the selected comment, the ladder runs exactly as today (ARCH-3, REL-2).
3. The gate keeps the namespace-pinned signer lines (§5.4), resolves `ssh-keygen` by an absolute path, and runs the capability probe once for each process (REL-1).
4. For each current bundle comment, newest first and once for each run, the gate writes the bundle line-2 bytes, the signature, and the kept signer lines to a private temporary directory (REL-3). `ssh-keygen -Y find-principals` names the principal. The gate fails closed on zero principals, several principals, or a wildcard. `ssh-keygen -Y verify -I <principal> -n dotbabel-evidence@v1` gets the bundle line 2 on stdin through the `input` option.
5. The gate checks the signer tier: the security-key flags for an `sk-` key (KD-11), and the declaration for any other key (KD-13).
6. The gate compares the signed bundle scope and `head_sha` with the pull request (KD-3). A bundle that passes steps 4 to 6 is a verified bundle.
7. For each current family comment, newest first, the gate hashes line 2 and looks for that hash under the comment's family in a verified bundle. It also compares the family payload's own scope and `head_sha` (KD-3). The first comment that passes is the selected comment. The existing rungs continue: payload, then the family rungs (§5.7).
8. Merge gate only: the gate computes the trust-root change (§5.3). If there is one, it runs step 7 on the current `trust-root` comments, and it compares their `changes` with its own result.

## Separate-user signer (optional tier, KD-6)

1. The agent writes a request `{repo, pr, head_sha}` to a spool directory that the signer user can read.
2. The signer, a systemd unit of user `dotbabel-signer`, fetches `head_sha` from the remote into its own checkout. It never reads the agent's worktree.
3. The signer runs the governed matrix from the base-ref configuration, in a sandbox with no read access to the key (SEC-3).
4. The signer writes the attestation comment body, and a bundle that it signs over that payload's hash, to an outbox. The owner's session posts both. A human bundle for the same head can name the other families, because any verified bundle can name a family comment (§5.7). The poster must still be in `trusted_associations`, because the trusted-association rung stays (ARCH-4). A separate bot account needs that list widened on purpose.
5. The signer's code is a pinned install that the signer user owns. It is never the npm-linked development checkout that the agent can edit.
6. The signer's principal is in `evidence.unattended_principals`, because its key is not a security key (§5.1).
